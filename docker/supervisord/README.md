# supervisord image: persistent rootfs ("VPS mode")

The `llama/supervisord` pod behaves like a small VPS: its root filesystem lives
on the `llama-rootfs-lvmssd` PVC (30Gi, btrfs, ssd-lvmpv), so `apt install`,
a custom Mesa in `/usr`, sshd, etc. survive pod restarts. Models, builds and
`supervisord.conf` stay on the existing `llama-models-lvmssd` PVC at `/root`.

## How it works

`ENTRYPOINT` is `/boot.sh` (runs from the image, before the pivot):

1. PVC is mounted at `/rootfs`; the new root is `/rootfs/os`.
2. If `/rootfs/os/var/lib/rootfs-seed/seeded` is missing, copy the image's root
   (`tar --one-file-system`, so `/proc /sys /dev /root /rootfs` are not copied) into
   `/rootfs/os.seeding`, then `mv` it to `/rootfs/os`. The rename is the commit
   point; a killed seed leaves only `os.seeding`, which is deleted on next boot.
   The seed records `packages.seed` (dpkg list at seed time) and `seeded` (date, hash).
3. Every boot: `make-rprivate /`, bind
   `/rootfs/os` onto itself (pivot_root needs a mount point), `rbind` `/dev`
   (includes `/dev/dri/renderD*`, `/dev/shm`, `/dev/termination-log`), `/proc`,
   `/sys`, `/root`, and bind the kubelet files `/etc/resolv.conf`, `/etc/hosts`,
   `/etc/hostname`. `/run` is a new tmpfs; `/tmp` stays on disk and is emptied.
4. `cd /rootfs/os; pivot_root . .; umount -l .` (the same trick runc uses), then
   `exec` systemd (see below), or without it run `/entrypoint.sh` ->
   `supervisord -n -c $WORKSPACE/supervisord.conf`.
   Because the whole mount namespace is pivoted (not chrooted), `kubectl exec`
   lands in the persistent rootfs directly. Anything kubelet mounts outside the
   paths above (e.g. a service account token) is left behind, which is why the
   deployment sets `automountServiceAccountToken: false`.

If anything in the prepare step fails (PVC missing, disk full, ...), the script
logs `[boot] ...` and boots the plain image so inference still works.

## systemd

If the rootfs has `/usr/lib/systemd/systemd` (the image installs `systemd
systemd-sysv dbus`), PID 1 after the pivot is systemd, and supervisord runs as
`rootfs-supervisord.service` (`/entrypoint.sh`, restarted on failure). Without
systemd in the rootfs (e.g. one seeded from an older image) it falls back to
supervisord under a small bash PID 1; `apt install systemd systemd-sysv dbus`
inside the pod and restart to switch.

Everything systemd-specific is generated by `boot.sh` into `/run` (a fresh
tmpfs) on every boot, so nothing in the persistent `/etc` depends on it:

- `/run/systemd/system/rootfs-supervisord.service` (+ `multi-user.target.wants`)
- `/run/pod.env`: the pod's env (`WORKSPACE`, ...) for the unit; services do
  not inherit PID 1's env.
- Masks (`-> /dev/null`) for units that would try to act on the **host**
  (the pod has `CAP_SYS_ADMIN`; they were outright harmful when it was
  privileged): udev (re-triggers host devices), `systemd-sysctl` (any package's
  `sysctl.d` would change node settings), modules-load, binfmt, remount-fs,
  pstore, timesyncd, networkd/resolved, gettys, kernel fs mounts, `tmp.mount`
  (keeps `/tmp` on disk), and Debian's own `supervisor.service`. See `MASK` in
  `boot.sh`. A unit file of the same name in `/etc/systemd/system` overrides a
  mask, deliberately.
- `/run/systemd/journald.conf.d/50-pod.conf`: `ReadKMsg=no` (don't ingest
  the host kernel log).

Logs: systemd and the unit write to `/dev/console`, which exists because the
deployment sets `tty: true`; that is what `kubectl logs` shows (with colours and
`\r`). Everything is also in the journal (`journalctl -u rootfs-supervisord`).

Stopping: the image's `STOPSIGNAL` is `SIGRTMIN+3` (systemd re-executes itself
on SIGTERM). systemd stops units (supervisord gets 45 s) and halts within the
60 s grace period. In the supervisord fallback, bash forwards it as SIGTERM.

`systemctl poweroff`/`reboot` inside the pod stop the container (it's a PID
namespace), and Kubernetes restarts it.

## Escape hatches

- Skip the rootfs without redeploying: `touch /root/.no-pivot` (models PVC)
  then restart the pod. Or set env `SUPERVISORD_NO_PIVOT=1` on the container.
- Keep the rootfs but skip systemd (supervisord as PID 1): `touch
  /root/.no-systemd` and restart, or env `SUPERVISORD_NO_SYSTEMD=1`.
  Remove the file/env to return.
- Factory reset: `touch /root/.rootfs-reset` and restart; the rootfs is wiped
  and reseeded from the current image on that boot (file is deleted).
  Offline alternative: scale to 0 and empty the PVC, or delete `/rootfs/os`.
- Because the plain-image fallback is always available, `kubectl exec` still
  works for repair even if the rootfs is broken.

## Image updates no longer apply automatically (drift)

After the first seed, `/rootfs/os` is the machine; new image builds change
nothing in it (including `/entrypoint.sh` and the Debian packages). To adopt a
new image either factory-reset (loses hand-made changes) or apply changes by hand
(`apt full-upgrade`, copy a new `/entrypoint.sh` from the plain image:
`touch /root/.no-pivot`, restart, then `cp /entrypoint.sh /rootfs/os/entrypoint.sh`).
Keep the Dockerfile's package list in sync with what you want after a reset.

Record hand-installed things so they can be folded back into the Dockerfile:

```sh
# inside the pod: what differs from the seed
dpkg-query -W -f='${binary:Package}\t${Version}\n' | diff /var/lib/rootfs-seed/packages.seed - 
apt-mark showmanual > /root/packages-manual.txt   # lives on the models PVC
```

Anything not under `/root` and not from apt (custom Mesa under `/usr/local`, `/etc`
edits) should get a line in `/root/rootfs-notes.md`.

## Optional: sshd (not enabled, nothing exposed)

Inside the pod: `apt install openssh-server`, put keys in `/root/.ssh/authorized_keys`,
`mkdir -p /run/sshd` (`/run` is cleaned each boot), `ssh-keygen -A` (host keys persist).
Add to `/root/supervisord.conf` (autostart off by default):

```ini
[program:sshd]
command=/usr/sbin/sshd -D -e
autostart=false
autorestart=true
stdout_logfile=/tmp/sshd.log
redirect_stderr=true
```

Start with `supervisorctl start sshd`. To reach it, prefer
`kubectl -n llama port-forward deploy/supervisord 2222:22`. Exposing it via a
Service/ingress is a deliberate separate change (the pod has `CAP_SYS_ADMIN`).
Do not use `PermitRootLogin yes` with password auth.

## Rollout

Flux applies `apps/` on push to `fresh-start` (Woodpecker triggers
`flux reconcile source git`), and Woodpecker builds the image on pushes touching
`docker/**`. Pushing therefore deploys. Two commits so the pod restarts once:

1. Commit 1 (image + PVC + this README): push. CI builds
   `gitea.lumpiasty.xyz/lumpiasty/supervisord:latest` and `:<sha8>`; Flux creates the
   rootfs PVC. Pod is untouched.
2. Get the new digest, put it in `apps/llama/deployment.yaml` (commit 2 carries the
   volume/mount; its image digest is a placeholder until step 1 finishes), push. One restart: seed runs
   (~1.1G image root: expect roughly 30-90 s extra), then supervisord starts.
   Total downtime about 1-2 min (pod is `Recreate`, GPU is exclusive).
3. Verify: `kubectl -n llama logs deploy/supervisord | grep '\[boot\]'` (expect
   "seeding", "seed done", "pivoting into /rootfs/os"); in `kubectl exec`: `findmnt /`
   shows the rootfs PVC device (not overlay), `ls -l /dev/dri` (only `renderD*`),
   `supervisorctl status`, then a request through llama-swap.

## Rollback

Revert the deployment to the previous image digest (and optionally drop the
rootfs mount); the old image's entrypoint ignores the PVC. Keep the PVC: the
installed system is still there. Quicker without a deploy: `touch /root/.no-pivot`.

## Known limits

- The pod is **not** privileged. It gets `CAP_SYS_ADMIN` (for mount, pivot_root
  and systemd's unit sandboxing) with seccomp/AppArmor unconfined. The GPU comes
  in as `squat.ai/gpu` from `infra/controllers/generic-device-plugin.yaml`, which
  injects only `/dev/dri/renderD*` (Vulkan/RADV; the GPU can't run ROCm, so no
  `/dev/kfd`). `/sys` and `/proc/sys` are read-only. `boot.sh` remounts only
  `/sys/fs/cgroup` (the pod's own cgroup namespace) read-write for systemd.
- Root in the pod is still real root with `CAP_SYS_ADMIN`, so this is
  hardening, not a sandbox. `hostUsers: false` would go further but needs the
  render node world-accessible and breaks the cgroup remount (locked mounts).
- `/dev/shm` stays the kubelet's 64M (same as before; `LLAMA_VRAM_ARENA` lives there).
- Mounts made by the boot script exist only in the container's mount namespace
  (gone on restart; redone each boot).
- `/run` is a tmpfs (256M); `/tmp` is on disk and emptied on each boot.
- `terminationGracePeriodSeconds` is 60 so apt/dpkg and llama-swap (stopwaitsecs=30)
  can finish before SIGKILL.
